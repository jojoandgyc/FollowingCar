# 录像对实时控制的资源影响：有界降载

## 本轮改动

仅修改 `video_recorder.py` 及主程序的录像配置绑定。未修改身份、PID、深度授权、转向和电机接口。
沿用异步录像，不改全局 OpenCV 线程数，不在录像中新增设备读取。

1. 录像线程使用 Linux 原生线程 ID 设置 nice=5（只降低本线程优先级）。
   无权限/不支持时打印一次提示并保留原优先级，不影响控制启动。
   不设置主进程或其他控制线程的优先级；不承诺原生共享工作线程完全隔离。
2. 主入口默认队列容量由 60 改为 12，减少低优先级录像长时间积压后的内存占用与追写负载。
   队列满先丢帧，不做无用 RGB 拷贝。元数据锁竞争时也立即返回，采集/视觉不等录像锁。
   丢帧路径只累计计数，不由采集线程同步打印日志；后台汇总打印。
3. `submit()` 仍复制一次帧，确保录像和主视觉不共享可写像素；录像后台在自己的副本上绘字，
   去掉第二次整帧复制。公开绘字接口仍默认复制，防止其他调用误改输入。
4. 长文本截断改为二分查找，字体布局缓存最多 256 项。
   重复文字使用字形/描边掩码缓存，最多 96 项、总像素数据最多 1MB；不缓存摄像头背景。
   当前 CAP、轮速、人速等变化仍按当前字符串重新绘制，不能用旧数值替换新数值。
5. 去掉随录像时长无限增长的“所有已写 CAP”集合。
   是否允许补充元数据由有界的待写 CAP 集合判断，写完即移除。
6. 原后台统计增加 `submit_ms(avg,p95,max)` 和 `metadata_dropped`。
   原轮速、目标速度、深度、身份、CAP/CTRL、CSV 时间戳和清晰度算法保留。

## 启动与回退

原命令不变：

```sh
./run_request_0428_modular.sh
```

如需对照原队列大小和线程优先级（不会撤销绘字优化）：

```sh
FOLLOW_VIDEO_QUEUE_CAPACITY=60 FOLLOW_VIDEO_WORKER_NICE=0 ./run_request_0428_modular.sh
```

容量限制 1–60；nice 限制 0–19。不会主动提升录像线程优先级。
FFmpeg packet-copy 后端、JPEG quality=90、分辨率、帧率与 250ms 叠字等待窗口不变。

## 代价与边界

优先保障控制，不承诺录像零丢帧或零开销。
队列满或元数据锁竞争时，可能丢录像帧或对应检测叠加信息。
保存下来的帧仍保持真实 CAP 和采集时刻；不伪造控制编号、轮速或不存在的画面。
用 CSV 的 `recording_capture_gap` 和 `recording_dropped_total` 检查丢帧。
固定帧率 AVI 丢帧后会播放加速，按真实采集时间分析或停车后使用既有 retime 工具。
`submit_ms` 包含图像复制和入队耗时，并非“零阻塞保证”；后台仍共享 CPU、内存和存储资源。

## 验证

24 项新增回归，与既有录像/轮速/人速/深度叠加测试合计 98 项通过。
覆盖元数据锁被另一线程占用时立即返回、满队列不拷贝、复制或入队失败清理、
无生产线程日志、每帧快照时间、缓存上限、不同背景不串帧、描边/透明度逐像素一致、
录像线程降优先级不改变主线程、后台原图隔离。
独立 `test_video_recorder.py` 自测通过。未打开实车摄像头或操作电机。
最终全套回归：3836 通过，3 项既有失败（目标距离配置断言、两项搜索方向断言）。
Python 编译及 diff 空白检查通过。

640×480 固定诊断场景，变化 CAP/清晰度，60 帧离线绘制，两轮对照：

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 绘制中位数 | 3.85 / 3.79ms | 1.31 / 1.31ms |
| 绘制 P95 | 4.13 / 3.83ms | 1.37 / 1.43ms |

这不是并发实车负载结果；不包含完整编码写盘，也不能据此宣称运控延迟下降相同比例。

下一轮同时关注：

- 稳态 `submit_ms` P95 争取 <2ms，不能出现随录像积压不断增大的趋势。
- 绘制 P95 和队列年龄下降，写盘耗时单列；不把等待叠加信息的时间算成纯计算。
- 录像丢帧、元数据丢弃数必须可见，避免“录像更快”只是大量漏帧。
- 视觉/控制延迟及跟踪 P95 不恶化，不能以录像完整性换取小车卡顿。

数值库单线程试验与本轮都可能改善资源竞争，下一轮变化不能全部归因于某一项。
