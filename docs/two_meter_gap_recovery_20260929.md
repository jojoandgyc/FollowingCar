# 距离拉大到2米：停车恢复与PI抗饱和

分析基线仍为 `run_request_0428_modular_logs/run_20260929_200957_54494_c3d555cc`，
不是上一轮锁外Depth改动之后的新实车运行。当前设定距离为 **1.40m**，不是2m。
本轮未启动摄像头、跟随进程或串口，也未修改0x005F、P/Ki、总RPM上限、身份阈值和授权期限。

## 为什么会越拉越远

1. **转向需求遮住了停车中的纵向恢复需求。**
   `_release_near_yaw_park_for_decision()` 原来只在完全没有运动动作时读取
   `parked_forward_resume_demand_rpm()`。停车时PI输出0，不代表制动后的纵向需求为0。
   有 `steer_left/right`（前进0、差速非0）或原地转向动作时，原代码跳过该预览，
   因而只能走纯回中的500ms驻留、停稳和后置图像流程，甚至被中心释放范围挡住。
   这不是身份丢失或目标距离不可用。
2. **早期请求与机械响应共同滞后。**
   小误差时P本来很小；恢复或制动再压低请求。等请求升高，轮速还需要时间跟上。
   原始日志不能把所有这些时间都算作串口发送耗时。
3. **积分曾被额外追赶请求错误冻结。**
   `总需求=max(P+I,追赶附加需求)`，原抗饱和仅比较总需求与输出/批准量。
   即使批准量已足够执行P+I，只要较高的附加需求受限，也会撤销本次正积分。
   但全轮82%的冻结不能全部归咎于此：真实制动、短授权和无可用采样间隔也需要冻结。

## 本轮修复

### 纵向恢复不再依赖“有没有转向动作”

没有正向/反向平移请求时，都可读取同一新鲜样本对应的停车PI需求。
仅有转向不再遮住纵向需求；真实反向运动仍保留原分支，不被前进预览覆盖。

该需求只走**已经存在**的前进恢复接口：可靠同UID、原始深度正在远离、
新鲜采样、真实距离超出目标范围等检查仍保留。
仍须先完成驻车电流释放/读回和FREE动作；预览不写速度包、不积分、不复活旧授权。
解除停车后，重复预览不能运动，新的物理深度样本才能通过原制动和加速约束恢复。
单纯转向/搜索、真正危险、身份不合格、反向需求和未知接近速度，不获得新的提前退出资格。

日志增加 `lateral_motion_present`、`translation_present`、`early_forward`，
便于检查带转向的前进需求是否确实进入了既有恢复路径。

### 按PI本身是否受限进行抗饱和

内部斜坡和最终批准量仍不变。只有P+I本身超出可执行输出时，才回退正积分；
附加追赶请求被限、P+I仍可执行时，允许按原Ki/真实采样间隔积累。
真实制动、重复/拒绝采样、零输出、停车预览、多次收紧批准和2RPM量化保护均回归。

当前参数离线例子：距离1.83m，P+I约88.7RPM，附加需求115.2RPM；
斜坡已允许102RPM时，原代码仍把新增积分清回0。修复后该50ms样本可保留0.008m/s积分，
不是把102RPM提高为115RPM。连续外部批准90或100RPM时，只学习到实际可执行的PI范围。

## 验收与尚未解决的边界

新增测试覆盖左右偏轴、释放范围内但仍有横向需求、真实PI/停车执行边界、
23类安全/时效反例、重复采样不续期、反向不抢占和PI积分冻结。
定向96项通过；最终全套 **6864项通过，3条原有配置提示**，耗时102.27秒。
修改模块编译和 `git diff --check` 通过。所有测试使用离线输入、假时钟/假执行器，不操作电机。

没有将2m设为新的加速阈值，也没有承诺任何走速下都不超过2m。
用户此前60RPM实测到90%约0.6s；仅拟合该数值的一阶模型又无法同时拟合约0.47s的t50，
不能用简化模型证明实际峰值。增加Ki的纯CPU对照对起步峰值改善很小且可能增加停车过冲，
因此本轮不提高Ki；正向变化率提前响应也仅做了模型研究，尚未接入实车指令。
