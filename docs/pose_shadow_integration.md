# 骨骼辅助跟随：融合方案与观察实验

日期：2026-09-16。当前阶段：只观察，默认关闭；未接入纵向、横向或 ReID 决策。

## 1. 功能分工与分阶段方案

保持现有 YOLO → ReID/IdentityBank → 身份绑定测距框 → Astra Depth → 控制器链路。
骨骼是同一已确认目标的辅助几何信息，不获得身份判定和电机控制权。

| 阶段 | 工作 | 进入下一阶段前的证据 |
| --- | --- | --- |
| A：当前已实现 | 同步 RGB、原始人体框、深度和 UID；后台姿态推理；比较两种区域的深度及中心 | 按场景统计可用率、拒绝原因、耗时；人工复核覆盖区域 |
| B：躯干测距辅助 | 可信肩髋点确定躯干内部区域，作为现有多区域测距的附加候选 | 有标尺/人工标注的对照集；背景误取减少；近距危险不漏报；失效及时回退 |
| C：横向中心辅助 | 将可信肩髋中心作为横向几何候选，比较抬手时相对框中心的抖动 | 固定站位抬手的中心误差、误转向次数改善；侧身/遮挡不引入偏移或额外延迟 |
| D：ReID 裁剪辅助 | 用骨骼调整躯干外观裁剪；保留原特征与原图来源 | 多人、遮挡、转身的身份评估；不能用类似姿态给不同人合并 UID |

阶段 B/C/D 仅为方案，尚未实现，也没有放宽现有深度时间期限、转向反馈或安全门。
不加入 IMU 转向反馈，不修改 PID、目标距离、轮速、原有身份确认规则。

## 2. 当前实现如何接入

### 已复用的数据

活动主程序原有 `_record_depth_diagnostic_rgb()` 将干净画面送入 `DepthDiagnostics`。
`AstraDepthRuntime.measure_target()` 原有诊断提供 UID、原始框、采集帧号、实际深度样本时间、
当前测距区域、候选/接受/保持距离及拒绝原因。

本次只在 `DepthDiagnostics` 加旁路，按**完全相同的采集帧号**与**实际采样深度时间**取已有数组。
没有在跟随主循环另开相机或重复跑 YOLO，没有重新调用控制用的测距过滤器。

`car_control_modular/pose_shadow.py` 负责：

- 工作线程内加载现有 ARM64 查看器的 `mp_pose.py` 和 ONNX 姿态模型。
- 每次仅一个目标；默认最多 2 次/秒、120 个样本，等待队列容量为 1，满时丢弃。
- 复用诊断环内拥有所有权且不再修改的 RGB/深度数组；模型、图像编码和文件写入不在生产线程执行。
- 输入最长 250ms；入队、推理前检查年龄，完成后记录 `within_age_budget`。
  这个 250ms 仅为观察门槛，不能覆盖当前控制链更严格的时间限制。
- RGB/Depth 到达时间差最多 50ms；这不是曝光同步标定结论。
- 要求明确的非镜像配准坐标空间，尺寸匹配；拒绝旧帧人体框、其他时间深度及未绑定 UID。
- 取肩膀 11/12 和髋部 23/24；可见性/存在置信度至少 0.6；拒绝出框、非凸、过小或塌缩的躯干。
- 肩髋四边形向内缩到 65%，降低轮廓边缘和手臂干扰。
- 只计算诊断区域的深度统计、中心偏差并写文件；不向控制层发布任何结果。

模型和适配器默认沿用现有文件，不复制第三方代码：

```text
/home/topeet/AstraSDK/samples/arm64_viewers/mp_pose.py
/home/topeet/AstraSDK/samples/arm64_viewers/models/pose_estimation_mediapipe_2023mar.onnx
```

可通过 `FOLLOW_POSE_ADAPTER`、`FOLLOW_POSE_MODEL` 指定其他本地路径。
缺文件、模型载入失败或写盘失败只禁用观察；错误写入日志。
这个 ONNX 适配器使用 OpenCV DNN CPU，尚未迁移 RKNN。线程隔离不等于没有 CPU 竞争，
本轮相机实验也没有同时运行完整 ReID、动作线程，下一阶段仍须测正常跟随负载。

### 记录文件

输出目录内包含：

- `manifest.json`：观察配置、模型/适配器/观察模块哈希。
- `observations.jsonl`：每次成功与失败观察、基线信息、姿态耗时、排队时间和结果年龄。
- `sample_*.jpg`：蓝色为现有区域，绿色为骨骼区域；用于人工复核。
- `sample_*.npz`：对应原始 RGB、深度、框及时间元数据，可离线重放。
- `summary.json`：提交、限频、丢弃、成功及拒绝计数。
- `inference.avi`：每次推理的骨骼和区域叠加视频，含失败帧；JSONL 记录视频帧索引。
- 相机专用工具退出后自动用 ffmpeg 导出 `inference.mp4`，便于观看；转码失败时保留 AVI。
- 相机专用工具额外保存 `evaluation.json`：采集帧数、观察统计和实际深度配置。

默认为快照/观察文本预留 48MiB、AVI 预留 16MiB，最多 12 组原始快照，每 5 秒至多一组。
视频固定约 2FPS，表示推理采样帧，不是 30FPS 全相机录像；显示原始时间，不补造中间动作。
AVI 编码缓冲可能使视频预算超出最后一帧的大小；退出后的 MP4 播放副本另占空间。
已存在目录不覆盖，观察目录随所在运行记录接受原有保留策略；需要保留的实验另存。
启动及清单等少量文本开销不计入图像/观察预算，快照与 JSONL 受预算约束。

## 3. 使用方式

### 3.1 离线回放，不打开设备

在项目根目录运行，输出目录必须不存在：

```bash
python3 tools/pose_shadow_eval.py \
  --input run_request_0428_modular_logs \
  --output .test_outputs/pose_replay_new --video
```

旧诊断中的异常前/后快照可能使用别的帧的人体框，工具会明确拒绝。
`--video` 将合格快照重新推理并导出标有 `SPARSE SNAPSHOT REPLAY` 的 1FPS 抽样视频。
每张保留快照展示一秒，源时间另行显示，不能把视频长度当作原始采集时长。
这类快照适合肉眼复盘，不能直接当成严格配对的测距样本。
离线回放不检查“距现在多久”，但仍检查包内帧号、深度采样时间和配准信息。

### 3.2 相机专用采样，不连接电机

先退出其他使用相机的程序。它不会替你停止其他控制进程。

```bash
python3 tools/pose_shadow_eval.py --live --duration 60 \
  --output .test_outputs/pose_live_new
```

这是已运行验证的独立采样工具，只有 RGB、Depth、YOLO 和姿态推理，没有导入/构造电机后端。
单人采集时使用 `identity_source=single_person_unverified`，不能拿来证明 ReID 身份保持。
没有人或出现多人时跳过；再次进入单人观察时更换观察编号，重置测距目标状态。
它读取当前 INI 中与 `AstraDepthConfig` 对应的字段，保留实际接受/保持距离供比较。

建议场景：先完整躯干正面静止，再依次抬手、侧身、弯腰、走近、遮挡；
多人及身份切换留给有 ReID 的正常流水线验证。不要仅按提示的时间段自动推断真实动作标签。

### 3.3 正常跟随中的旁路观察（尚未做完整负载实车验证）

```bash
FOLLOW_POSE_SHADOW_ENABLE=1 ./run_request_0428_modular.sh \
  --config car_control_modular/config/reid_runtime.ini
```

**这是原来的实车跟随命令，会照常启动电机控制；它不同于上面的相机专用采样。**
旁路结果写入本次 `log_dir/depth_diagnostics/pose_shadow/`。
需要原有深度诊断开启（正常启动默认开启）；如果禁用深度诊断，骨骼旁路也不启动。
本次没有运行此命令，没有改变普通启动的默认行为。
撤销观察只需不设置 `FOLLOW_POSE_SHADOW_ENABLE` 或设为 `0`。

## 4. 如何解释数据

- `bbox_region_depth` 与 `pose_depth` 都是同一深度帧上的诊断统计，使用相同有效值范围和中位数方法。
- 现有区域取并集，避免重叠像素重复计数。姿态区域为内缩四边形。
- 这两个中位数都不是现有过滤、跳变确认和前景选择之后的控制距离。
  真正的原控制值另记为 `runtime_candidate_m / runtime_accepted_raw_m / runtime_filtered_or_held_m`。
- 没有标尺真值时，两者相差少不能证明更准确，相差多也不能证明骨骼更好。
- 记录了原始四肩髋点、输入画面和区域才能人工确认模型是否把腰部误认为髋部；仅有高置信度不够。
  当前快照保留原图和区域，新增 JSON 同时保存可用的 33 个关键点及其置信度。
- 低频与稀疏快照适合观察覆盖率和失败类型，不能证明 30Hz 控制效果或连续抖动已经改善。
