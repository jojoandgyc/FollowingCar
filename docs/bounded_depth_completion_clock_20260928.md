# 转动历史深度：开始资格与完成资格分开

## 修复对象

19:37这轮 CAP193～370 中，历史深度路径尝试23次，实际补入10个新深度；
其中 CAP294、330、360、362 的4次新测量在采样完成时被丢弃。
当时真实深度年龄分别为130.4、99.9、119.4、124.5ms，均未超过180ms；
框与深度的采集间隔也没有超过180ms。失败的是计算结束后的框年龄超过250ms。

旧函数将“此框还能否开始一次新测量”与“已建立的框—深度关联是否仍有效”
放在同一项完成检查里，导致合法关联被处理耗时再次否定。

## 现在的边界

1. 上层仍检查当前UID、检测框来源、边界、CAP与原采集时间；
   开始使用历史深度时，框年龄仍不得超过250ms。
2. 实际取得相机深度锁、选择物理帧时，再用当时的真实时间检查开始资格。
   等待锁不能让已经过期的框开始新工作。
3. 选择后保存不可变证据：UID、CAP、原框、RGB采集时间、物理深度时间、选定时间。
4. 采样完成和融合前分别核对同一证据：原关联偏差必须仍为0～180ms，
   同一物理帧当前年龄必须仍不超过180ms，不能换UID、换框、换时间戳。
   不再因为处理完成时RGB框年龄超过250ms，就抹掉已经建立的关联。
5. 超过250ms的框不能继续发起新的历史测量；重复深度仍不能成为新测量。
   物理深度超过180ms、缺少证据或证据不匹配，继续拒绝。

该证据只证明一次测量的来源，不确认身份、不更新模板、不独立授权电机。
主控制锁、UID/search/hazard/停车检查及最终运动读取均未修改。
前进授权继续使用真实深度时间加原期限，不使用处理完成时间续期。

## 验证

`tests/control/test_bounded_depth_completion_clock.py` 使用实际
`AstraDepthRuntime → SensorRuntime → DistanceRuntime/fusion` 路径，
输入合成深度像素并推进CAP294/330/360/362的日志时钟参数。
这验证的是时间门控和测量接续，不是对真实场景误差或停车轨迹的承诺。

覆盖：跨250ms完成但物理帧新鲜、物理帧真过期、等待测量/相机锁后才开始时拒绝、
UID/CAP/ROI/时间戳篡改、返回融合前过期、异常后清理旧选择证据、
完成后不能重复发起测量、授权期限不延长、最终UID切换/停车仍撤销运动。
同时覆盖等待相机锁期间新深度到达，不得用进入函数前的旧时间误判为未来帧；
选帧时间缺失或格式异常时安全拒绝，诊断日志也不能因此抛出类型错误。

相关深度与授权回归228项通过；未操作硬件。
