# CAP333 搜索制动后，居中目标恢复前进

## 原因和改动边界

日志 `run_20260921_220904_68061_e711b8cc`：CAP333 下发 NORMAL，CAP357
已完成停稳/停车后图像检查，却留下 `search_reacquire_brake` 刹车保持。
运动命令负责解除保持，但深度授权入口拒绝任何刹车保持，视觉前进又由
Depth 统一接管，形成相互等待。之后约 5 秒有 66 次距离 PID 输出
（36～113 RPM），却没有新前进授权或速度下发。

本次只增加该类型停车的独立恢复入口，不修改 PID、RPM、距离设定、
图像/深度有效期、反转保护或正常停车释放策略。

## 恢复条件

搜索停车请求记录当时活动 UID；等待结束仍不直接授权运动。视觉流程拿到
新的可靠深度后，在原有授权入口执行以下检查：

- 只允许 NORMAL、标签为 `search_reacquire_brake` 的保持；该次等待已结束，
  实际 STOP 和停稳证据属于同一停车请求。
- 活动 UID 与停车时相同、唯一可靠目标，原始 YOLO 深度框绑定当前 CAP
  和采集时间；当前视觉/控制状态允许跟随。
- 新深度不是重复/乱序，原始与使用距离都在设定距离及死区之外；已有
  控制决策明确要求前进。原来的危险、近距锁存、可信度检查继续生效。
- 新图像在实际停车、停稳之后；重新检查新鲜双轮停稳反馈，硬安全检查
  失败或异常均保持停车。深度须为停车后的真实新样本，不能靠处理时间续期。
- 队列中有受保护 STOP 时，不得清掉它或解除保持。

通过后，在命令/电机锁下清理旧动作、旧横向意图和旧授权，推进命令版本，
仅解除这次搜索驻车。随后重新走现有纵向控制及授权提交。恢复入口不写
电机，不恢复旧速度。授权若最终未通过，旧指令不能借机复活。

## 日志与验证

- `search_brake_depth_resumed`：恢复 CAP/UID、新深度时间、实际停车/停稳
  时间；`old_authority_restored=False`，下一步为新的深度授权。
- `search_brake_depth_resume_rejected`：身份变化、尚未停稳、证据过期、
  硬安全检查拒绝等原因。

下一轮重点确认：

1. 出现 `search_reacquire_brake_settled` 后，居中远目标获得新可信深度时，
   同轮能够出现恢复及 `depth_linear_authority`，不再必须等一次转向。
2. CAP361 式“深度新鲜、距离偏远、PI 为正，但搜索刹车一直挡住授权”
   要求 0 次；同时记录新合格深度到实际非零轮速下发的延迟。
3. 旧帧解除、无可信深度恢复、危险保持被解除均要求 0 次。
4. 单独检查首次转向的过冲和恢复前进后的距离变化，不能仅凭恢复日志
   判断实车效果已经改善。
