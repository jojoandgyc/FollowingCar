## 修复1：1RPM不是曾经下发的正向授权

`controllers._update_distance_pid()`原来使用诊断`output_rpm>0`判断上一帧有正向需求，
再发现运行层没有live grant就触发`suspend_longitudinal_authority`。

但当前200RPM标度采用百分比向下量化：1RPM→0%。控制器内层已经收到最终0RPM反馈，
运行层也正确不建立前进授权；外层却仍拿量化前1RPM当成“曾有正向授权”。
于是连续新样本变成：

`实测约1RPM → 恢复请求1RPM → 量化0% → 没有live grant → 恢复重新开始`。

CAP2074两次、CAP2076两次均出现该链。制动上限约51RPM，却因恢复返回1RPM。
CAP2080恰好实测0.5RPM使请求向下取整成0，反而避开旧`>0`检查，下一次才请求27RPM。
这说明不是“越低速越难起步”的电机特性，而是代码把1RPM和0RPM处理成了不同状态。

修改为按同一实际百分比换算判断旧正向需求：量化成0的请求没有失去过正向授权，
下一张合格新深度可从实际已批准的0RPM继续正常斜坡。
不向上取整、不增加固定起步脉冲、不借断档补加速时间。
真实授权撤销、停车、拒绝、过期仍由PI原有状态复位。

实函数回归：修复前1.0/1.5RPM两例稳定失败；修复后新样本间隔80ms，
可产生至多19.2RPM的斜坡预算（实际百分比量化后18RPM），而不是继续输出0。
这是无硬件指令结果，不等于小车在80ms内已达到18RPM。

## 修复2：停稳后结束旧搜索交接，重新由正常跟随检查接管

CAP2028/2031交接证据逐渐超过210ms，新Depth仍合法但旧搜索制动义务未解除，
执行器因此把整对轮速归零。CAP2035之后已有独立双轮零反馈，
本轮使用已完成零指令和后续新反馈证明旧转动已消失，再由新鲜可信视觉结束旧交接。
候选自身连续、旧图像过期或单纯等待时间经过，都不能单独证明停稳。

新证据由轮速发送线程在成功发送后发布不可变快照，视觉控制线程只读核验：

- 同UID、同搜索交接阶段，连续成功的双轮零速回执。
- 两份独立、互不重叠的编码器读取都开始于首次零包写完之后，间隔40–150ms。
- 反馈无错误，双轮绝对转速≤1RPM、原始/滤波角速度均≤2°/s；当前反馈也必须新鲜并停稳。
- 当前新图像身份已确认且仍在原210ms范围内；图像采集也晚于零包。
- 中间出现非零包、STOP、停车、故障、回执断档、换UID或新搜索阶段，原证据立即不可用。
- 缺少完整回执/读取时间的兼容后端不启用该路径，不因此异常退出。

间隔62.83ms，完整读取均晚于16404.242929221的零包完成。

这可以提前结束旧搜索约束，避免该分支继续造成03.026–03.198的约172ms零速段；

## 诊断改进：处理用时不等于图像年龄

原`result_age_ms`实际是开始处理到视觉完成的耗时，未计采集后等待。
CAP2074旧字段81.94ms；结合采集CSV估算，真实采集→结果约142ms，→决策约154ms。
这里是壁钟/采集钟关联估算，不冒充精确同钟测量。

新增同一monotonic时钟记录：

- `capture_to_pipeline_ms`：采集到开始处理；
- `capture_result_age_ms`：采集到视觉结果；
- `capture_decision_age_ms`：采集到控制决策完成；
- `capture_clock_valid`：时钟链合法性，非法/未来/逆序不伪装成0ms。

旧字段保留并标明`legacy_result_age_scope=processing_duration`，本轮不改变stale门控
或任何授权时间，避免以诊断修复为名隐式扩大/缩小运行权限。
