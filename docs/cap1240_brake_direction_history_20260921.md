## CAP1237 的约 224ms 是什么

CSV 采集墙钟为 20:23:36.356130，观察入口日志时间约为 20:23:36.580，
差约 223.9ms（日志毫秒精度，不能视为精确性能采样）。

视觉总处理耗时为 192.34ms：

- YOLO 总计 46.14ms：预处理 4.71、推理 27.96、解码 13.41、NMS 0.06ms。
- ReID 总计 20.70ms；日志中的预处理、全身/局部推理、后处理存在嵌套，不再相加。
- tracker 总计 114.78ms：关联阶段 85.07ms（其中 Kalman 更新 79.77ms），
  几何 0.08ms、竞争比较 7.35ms、证据 0.46ms、轨迹记录/身份处理 21.79ms。
- 视觉总时间与以上三个顶层总计相差约 10.72ms，含其他处理、调度及未单列开销。

约 224ms 与 192.34ms 的差约 31.6ms，包含采集后进入 pipeline 前的等待，
以及视觉完成到方向观察入口的处理；旧日志不能精确拆分两者。
`control_ms=28.11` 统计到整个控制阶段结束，不是到观察门控的时间，不能全数叠加到 224ms。
同理，CAP1240 的处理时间 146.81ms 不等于它在观察入口约 213.2ms 的真实采集年龄。

## 实现

1. 停车历史观察独立设为最多 500ms，以真实采集时间计算，不重写采集时间。
2. 仍要求同活动 UID、唯一已分配且本帧更新的记录、当前 CAP/时间戳一致的身份来源、
   原始检测框有效、身份/质量/几何/竞争/排除检查通过。
3. 重复、倒序、未来、无效时间和超过窗口的样本不能补录。
4. 补录不执行 PID、不赋身份、不更新图库、不刷新深度或电机授权、不解除停车。
   等待结束沿用既有恢复接口，清除停车前方向状态；下一次正常搜索判断读取新历史。
5. 整帧超时分支仍先执行原安全撤销，然后仅在搜索制动等待尚存时补录历史。
   顺序很重要：安全处理会将当前采集槽标为 stale，不能在它之前写入后又被覆盖。
6. 等待日志增加 `capture_age_ms`、`capture_to_pipeline_ms`、`vision_processing_ms`、
   `history_max_age_ms`、`motion_max_age_ms`、`motion_authorized=False`。
   计时信息绑定 CAP 和采集时间；不复用上一帧计时。
