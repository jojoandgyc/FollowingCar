# 普通距离停车恢复：实施方案与当前进度

## 本轮解决的问题

17:25运行中，CAP746在1.427m正常停车后保持刹车；CAP783距离1.58m已需前进，
但视觉纵向已交给Depth30，Depth30又被`brake_hold`禁止处理。直到CAP822出现
左转命令才解锁，总保持4.044s。CAP781–842零指令占81.3%，其中2.409s来自
此前保持。应修复恢复入口，不应删除安全停车或提高RPM掩盖等待。

## 已实现：区分普通停车，允许观测驱动恢复

- 只将来源明确的`queued_action_stop_signal`、对应
  `lateral_zero:near_distance_rotation_only`、正常可见UID的停车标记为
  `follow_distance_hold`。搜索、未知停止、急停、安全保持和故障不获此资格。
- 新类型停车仍按原方式停车/保持，不产生轮速。允许原始YOLO框资格通过时读取
  最新Depth，也允许Depth30继续测量，但保持未解除前Depth30不执行PID/动作发布。
- 恢复需要同UID、新鲜原始框、无危险/障碍/刹车锁存/目标锁存、可信且<=150ms
  的编码器反馈，没有明显倒转；保留原始Depth180ms时效。
- 两张不同物理Depth必须发生在停车之后，间隔<=180ms；raw和used都超过
  `max(设定距离+0.03m,刹车距离+0.10m)`，两者差<=0.25m。
  相邻raw变化<=`0.05m+2.5m/s×dt`。这些是保守恢复条件，不是误匹配概率保证。
- 同一物理帧/可信复用不累计也不重置计数；真实不可信/危险样本清除确认链。
- 释放前再做实时安全检查，并在电机锁内复核停车事件对象、UID、安全标记和
  样本截止时间。新安全事件、检查异常或期间深度过期，都不能释放。
- 解除只撤销这个普通保持；旧纵向授权被丢弃，交给当前样本重新经过现有PID、
  恢复限速和总速度限制。不是直接恢复停车前速度，不改变搜索/ReID阈值。
- 视觉/搜索身份事件变化清除旧恢复事件；安全/故障停车覆盖普通标记。

本轮不更改50ms周期、180msDepth期限、60%上限和PID增益。
新的入口只解决此种已识别普通距离停车；不是让所有`brake_hold`自动释放。
正常启动会使用此修复，不需要新的相机标定来验证停车恢复。

## 下一轮无危险场景验证

准备急停，沿用现有启动脚本、当前速度限制。先在设定距离附近正常停车，保持
目标处于中心，再让同一目标缓慢远离。不要靠左右晃动触发转向来“帮助”解除。

验收链：`follow_distance_hold_started` → `observe_wait` → `ready` →
`follow_distance_hold_released` → 新Depth授权 → 非零正向轮速。
必须另测目标不动、突然靠近、遮挡、UID变化及危险输入；保持期内不能偷发前进。
软件回归包含故障注入；不要为测试在实车前制造碰撞危险。

`tools/follow_metrics.py`增加：

- `control.distance_parking_events`：started/released和每种观测结果计数。
- `control.distance_parking_release_ms`：普通停车至确认释放的耗时分布。

held_ms包含人仍站在保持区的时间，不等于从“人开始远离”到动作的纯响应延迟。
后者应以首次合格新Depth和实际轮速下发时间另行对齐分析。
结合零指令时间、有效深度Hz、无基速比例和距离变化率分析，不能只看release日志。
旧日志没有新字段时为空，不能解释为没有发生普通停车。
