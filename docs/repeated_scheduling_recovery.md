# 短断档恢复：保留进度，不延长电机授权

## 本轮修复

只修改纵向调度断档后的恢复限速和诊断，不改PID、RPM总上限、身份、搜索、
人体框250ms窗口或物理Depth180ms期限。直接运行原启动脚本生效。

原问题：`_note_depth_quality_failure`每次清掉动态恢复；下一次新深度将已经
被限低的批准速度重新当作上限，重新开始400ms恢复，可能一直锁在24RPM。

现在：

- 明确旧ROI/重复观测、同UID仍可见、无危险/障碍/距离异常时，只保留恢复状态。
  用最后通过检查的物理样本计时，参考最多保留500ms（原参考上限），失败尝试
  不更新时间、不增加速度、不延长原400ms恢复结束点。
- 500ms是恢复记忆期限，不是运动许可。超过180ms的物理Depth仍不能授权前进。
  丢目标、搜索、危险、跳变、背景异常或参考过期仍清除恢复状态。
- 上次批准速度只作为起步参考；新鲜且合格的测量到达后，按当前请求、上一恢复
  输出、实测轮速和既有加速限制向上恢复，不再受最初24RPM固定上限约束。
  单次使用物理采样间隔最多100ms；开始按50ms步进；加速度不超过原配置及240RPM/s，
  输出还受“实测轮速+150ms加速量”限制，近距/明显闭合等仍走原严格路径。
- 正常连续性快捷分支不能绕过正在执行的动态恢复。
- 重复样本不能推进恢复；允许减速，但后续重复样本不能撤销这次减速。
- 到400ms并不自动放行完整PID：必须有新样本，且实测轮速允许的输出已经能达到
  当前请求，才结束动态恢复。车轮停滞时不会仅凭时间到而跳到高请求值。

本轮不实现“旧指令持续1.5秒”，不将旧框当作独立Depth定位，也没有接入新的
独立深度跟踪控制权限。是否扩大视觉等待窗口需另行验证目标关联。

## 诊断与下轮验证

新增日志`depth_scheduling_recovery_gap action=pause/discard`；恢复日志追加
`ramp_end`、`ramp_completed`、`requested_rpm`和`measured_envelope_rpm`。
`previous_approved_rpm`现在表示本次恢复最初的批准参考，不再是固定限速上限。

`tools/follow_metrics.py`新增同UID/物理样本去重的暂停、完成、超过初始批准值计数，
以及恢复状态丢弃原因。旧日志没有新字段时不能把零次事件解读为已验证无问题。
已有恢复启动次数、恢复限幅损失、零指令时间、短掉速和距离指标口径不变。

上轮CAP119~346的分析作为参考基线；不同路线/人速并非严格对照：

| 指标 | 修改前参考 | 下一轮试验目标 |
|---|---:|---:|
| 移动平均绝对距离误差 | 1.038m | ≤0.70m |
| 移动最大距离 | 3.492m | ≤2.70m |
| 零轮速指令时间占比 | 17.62% | ≤12% |
| 批准速度短降>10RPM | 7.22次/10秒 | ≤5次/10秒 |

另外直接验收根因：同一次合格短断档恢复只有一次start，后续是pause/advance，
`ramp_end`不后移；新鲜测量/请求/实测轮速允许时必须能超过初始24RPM。
只在实测轮速支持时提速，不要求轮速不动也必须超出初始批准值。
恢复启动频率和限幅损失应下降，但不能以取消安全停车换取这些指标。

保持1.5m设定、P24与相同路线/走速，明确移动起止CAP；站定单独统计到1.5±0.15m
的时间和最小距离，目标最低不小于1.40m，上轮为1.418m。目标值非已实现效果。
不要本轮同时切换P36，以免混淆恢复修复的影响。
