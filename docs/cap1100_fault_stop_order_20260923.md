# CAP1100～结束：故障停车只写 STOP

## 证据与边界

`run_20260923_154030_23826_fac23090` 中，CAP996 请求的 NORMAL 于
15:41:24.804 完成，25.357 已完成 0A 读回和一次零速退出，27.372 因
`post_release_settle_timeout` 锁存故障。CAP1100～1147 约 2430ms 没有非零
运动目标，编码器仍有明显往返运动。不是上轮的 5A 永不退出。

原 `send_stop(emergency)` 顺序是：双轮零速 → 双轮 STOP=1 → 双轮零速。
周期故障保持也重复这条路径。另有后端 `send_targets(0,0)` 绕过故障运动
拦截的入口。不能只看日志中的 emergency 就认为驱动器一直处于紧急制动。

振荡在第一次故障停车前已存在，本次修复不声称这条命令顺序是所有振荡
的唯一原因，也不声称已验证真实制动能力。

## 修复

- EMERGENCY/FREE 只下发相应 STOP，不写前置/后置零速，不等待零速延时。
  每次保持刷新同样只写 STOP，避免临时回到速度控制命令。
- NORMAL 原有前置清零、恢复 5A、STOP=0 的流程不变，STOP 后不补零速。
  普通驻车仍遵守当前 **500ms** 电流期限，未修改该参数。
- 故障锁存后非零目标继续拒绝；零目标转为 EMERGENCY 保持，不再进入
  `prepare_speed_mode()` 或写速度寄存器。旧 NORMAL/驻车刷新仍转为急停。
- 下发 STOP 前就清软件 `motion_armed`，即使部分写入失败也不能保留
  “已武装”状态；失败不打印发送成功，不补零速，故障保持仍可重试 STOP。
- 停车日志新增 `stop_registers_sent=0x0040,0x0044`、`stop_value`、
  `pre_zero`、`post_zero`、`final_motor_command=stop`、`stop_write_ms`、
  `current_uncertain` 和 `physical_stillness=unverified`。

协议的 STOP 寄存器只支持写入，不能添加伪造的“停车状态读回”。现有
双轮驻车电流读回、编码器位置/速度/错误码日志继续保留，未额外增加串口
轮询负担。停车日志中的电流是最近一次切换读回缓存，若不确定会明确标记。
