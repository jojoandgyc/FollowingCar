# CAP524 附近突然停止：串口事务故障

## 已确认的直接原因

运行：`run_20260928_234859_64734_2128e47a`。

- 23:49:29.091：最后一次成功的 FOLLOW20，依据 CAP521，归一轮速目标为 15/1 RPM。
- 23:49:29.309：`motor_write_fault label=FOLLOW20 error=no response from driver`。
- 23:49:29.320～.321：独立尝试双轮急停，执行器锁存故障。
- 23:49:29.331：主程序进入退出流程；23:49:30.213 完成退出。

对应 `request_0513_modular.log` 第 10271、10288～10317 行。CAP524 仍检测到
UID1，置信度 0.904。故障前 CAP521 最近一次深度控制约 1.52 m，但等待串口
期间旧深度授权已经到期，不能说故障发生时旧距离仍有运动授权。

这是上一轮新增的写故障保护触发，不是 YOLO 完全漏检，也不是 PID 请求
始终为零。一次无回执既不能证明电机没执行，也不能允许重放旧速度。

## 根因边界

本轮只有一次写超时，没有此前持续的编码器读失败，记录的错误码均为 0/0。
上轮没有同类超时。原日志没有记录失败轮侧、寄存器、请求/响应字节和事务
起止，因此不能区分电气干扰、从站瞬态、主机调度或帧时序。

确定的代码缺口是：外部客户端连续 `write/read` 后立即进入下一事务，既
不执行 RTU 帧间等待，也不检查实际写入字节数。上层记录的左右读取调用
间隔中位数仅 0.583 微秒；这不是线上电平测量，不能单凭它断言本次硬件
超时根因。模拟要求帧间静默的从站能够复现原客户端第二请求无响应。

RTU 高于 19200 baud 推荐 1.750 ms 帧间静默，低速按 3.5 字符时间计算。
依据：[Modbus Serial Line V1.02 §2.5.1.1](https://www.modbus.org/docs/Modbus_over_serial_line_V1_02.pdf)。

## 本轮修复

新增本地 `motor_rtu.py`，在真实客户端构建后、第一次启动电机 I/O 之前接入；
外部 `/home/topeet/lianzhan` 库和实车参数不修改。

- 完整事务串行化，所有速度、STOP、编码器和电流寄存器操作共用帧间等待。
- 保持原 150 ms 配置预算，剩余预算用于碎片读取，不重发原请求；短写明确报错。
- 校验 CRC、从站、功能码、寄存器和值/数量。`0x10` 回执不含速度值，单凭
  内容不能区分同地址的旧回执；发生事务失败后按下述规则禁写，不能靠重新
  收到一个格式正确的 ACK 恢复运动。
- 失败后锁存响应流不确定。即使下一回收到合法 STOP 回执，也不解除运动
  故障。禁止再次写速度（包括 0RPM），防止旧 `0x10` 回执被当成新的零速确认。
- 仅保留紧急 STOP、退出清理所需的停车电流清零、不可返回控制使用的只读
  诊断。双轮 STOP 仍分别尝试，一侧失败不跳过另一侧。
- 编码器事务失去可信响应归属时，独立执行循环也能发现并停机，不等新
  视觉命令才处理。没有自动恢复运动。
- 初始化失败也将链路故障同步到 backend；不能通过同一实例再次初始化
  换一个新通信对象，把未解决故障清掉。
- 出错记录具体轮侧、原始请求目标、右轮是否获得回执，以及事务序号、
  阶段、寄存器、有限长度 TX/RX 和最近事务摘要。正常运行不逐包打印大日志。

接口超时不等于硬实时保证：支持 `write_timeout` 的串口按剩余预算配置；
外部 POSIX fallback 的底层 `tcdrain` 若卡住，Python 不能强行在 150 ms
中断它，只能在返回后检测超期。驱动类型和能力会记入启动日志。

## 验证及下轮检查

测试使用模拟时钟、内存串口及真实客户端方法，不打开设备。覆盖正常接入、
连续事务、短写/短读、无响应、CRC/地址错误、迟到 ACK、双轮 STOP、只读故障
升级，以及故障不能自动解除。随后运行电机和全套无硬件回归。

本轮修复的是明确的串口处理缺口，不能保证所有物理通信超时消失。下轮应
确认 `motor_rtu_guard_installed` 生效；若仍停机，根据新增事务记录区分失败
位置，不继续盲调 PID、ReID 或延长距离授权。
