# 搜索方向历史提示的生命周期修复

## 问题与范围

2026-09-15 22:42 运行中，CAP285 的目标在右侧。CAP288、290 的丢失等待动作仍
向右，但首个丢失帧已经把 CAP204/205 的历史回算 left 存入内部搜索方向；到
CAP291 正式搜索时没有重新解析，导致 CAP301/306/313/318 持续左搜。

本次只调整历史提示生命周期和搜索入口，不改变 RPM、PID、ReID 阈值、确认帧数、
Depth、障碍保护或电机下发。

## 处理规则

- 主视觉记录目标所属的可见几何后，结束旧丢失事件并清除旧历史提示；已有映射的
  低质量目标也覆盖该路径，不要求必须经过“强确认解除搜索”入口。
- 每次丢失以首个主控丢失 CAP 为事件标识。历史任务、提交结果与消费均检查该标识，
  防止同一 UID 的上一轮结果串入当前搜索。单次事件只安排一次回算任务。
- 提示携带最早一张有效证据的采集单调时间戳，提交和消费均复核现有 0.70s
  配置窗口。不能用计算完成时间续期，也不能用重复帧凑确认数。
- `missing_confirmation_pending` 只表示尚在确认丢失，不允许此时消费历史回算。
  等待阶段原有的“最新可信方向低速保持”不变，不新增等待。
- 正式进入搜索时，对未决方向或历史回算方向再次执行：目标历史解析 → 最新可靠
  目标侧 → 属于本事件且有效的历史提示。按时间确认丢失时无需额外等待帧数。
- 已确认候选授权的方向不被这一复核覆盖；已经开始的搜索仍保留方向与角度覆盖
  计量。未确认的 detector-only 人物不能清除事件或改变冻结方向。

## 日志与验证

`historical_direction_hint_ready` 增加 `loss_capture` 和 `evidence_timestamp`。
失效/拒绝输出 `newer_target_visible`、`loss_episode_changed`、
`evidence_expired_or_future`、`active_uid_changed`。
方向解析增加 `history_checked`、`selected_direction`、`selected_source` 和
`search_entry`，避免把 pending 的默认零样本字段误读成没有目标历史。

无硬件测试位于 `tests/control/test_historical_direction_episode.py`，覆盖普通/低质量
目标恢复、CAP285→291、有效历史回算、跨事件晚到结果、过期证据、正式搜索复核、
候选保护、异步服务及按时间确认。实车仍需验证：右侧消失后不应再引用早于后来
可信目标的左侧回算；人物交叉时未确认候选仍不能任意换向。
